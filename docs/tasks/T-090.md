## Why (evidence)

- A reusable fit serves T-089 and T-093 now, and hair and new characters later.

## Acceptance criteria
1. **Tool `tools/fit/`:** given a character spec, optional overrides, a list of spec parameters with bounds, and
   reference views (front, 3/4, side), it builds the candidate, renders cheap Workbench silhouettes/landmark passes
   with the reference cameras of `reference_index.json`, scores them against the reference landmarks and masks, and
   searches the parameters (bounded, deterministic seed, a build/render budget given on the command line).
2. **Output, never a spec edit:** a proposed override JSON, a score table (start → best, per view and landmark), and
   an overlay sheet (reference mask vs candidate outline). It writes only to its `--out` folder; it never writes
   `assets/characters/**`.
3. **Then the standard review:** for the proposal, one cheap first frame (`tools/review/recipe.py preview`) and one
   T-087 strict sheet (`recipe.py sheet`); the owner approves. Adoption into a candidate is done by the task that
   owns that character area (T-089 face, T-093 garments).
4. **Demonstration:** one face parameter set on the boy (eye opening, brow spacing) and one on the girl, each from the
   current spec; report wall time per iteration and in total.
5. Character-agnostic code (no character ids). Tests: parameter-bound handling, score function on synthetic masks,
   determinism (same seed, same proposal), refusal to write outside `--out`. No test loosened, no frozen or published
   file changed.
6. `tools/fit/README.md` (one page: inputs, outputs, how to adopt a proposal).
