## Acceptance criteria
1. One release manifest (guarded file; propose its path in your first STATUS, e.g. `pipeline/charsys/release_manifest.json`)
   lists each published character version that may use opt-in features, with the features and an owner decision ref.
   `tools/version_switch.py` writes/updates the entry as part of making a version CURRENT (same run, same commit).
2. One check: a published spec may use an opt-in feature only if its version is listed for that feature with a decision
   ref. It replaces the per-feature guards: `test_hair_r4/r5/r6`, `test_hair_v3_r2/r3`, `test_hands_r2`, `test_face_r5`,
   `test_face_v3`/`v3b`, `test_face_t168`, the `closed_fill` guard, `test_guard_allowlist.py` + `owner_approved_candidates.json`,
   and the allowlist role of `tools/shared_character_allowlist.txt` if it only serves that purpose. Only the "nobody uses X"
   parts go; any other assertion in those files (build, weights, geometry) stays, moved if needed.
3. Kept unchanged: byte-immutability of published assets, `tools/frozen_manifest.txt`, the asset-store guard
   (`pipeline/charsys/tests/test_asset_store_guard.py`), all goldens, the owner decision ref required for CURRENT.
4. Negative tests: an unlisted version using an opt-in fails (like the `9.9.9-test` case in `test_versions.py`); a listed
   version without a decision ref fails; a listed version using a feature it is not listed for fails; editing the manifest
   without the guard trailer fails the guarded-paths check.
5. Coverage mapping in the README: a table "old guard (file::check) → new check (file::test)" for every behaviour the old
   guards caught, each with a test that proves it is still caught. Send the table to the Supervisor BEFORE asking to merge.
6. Current state passes: boy 2.3.0 / girl 0.14.0 / third 0.1.0 and every other published version are listed as they are
   today (no behaviour change). Full `tools/check_all.py` green locally; then a full gate on the branch.
7. `docs/process/ASSET_STORE.md` (or the release section it points to): the rule in a few lines; new feature tasks add no
   per-feature guard.
