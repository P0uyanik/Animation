# T-086: CI efficiency (Phase A, round 2)

Implementer: Claude (cloud) · lane A · path A · branch `t-086-claude-ci-efficiency` from `origin/main`. Starts after
T-085 merges (same workflow file). Round 2 plan A2. Owner-approved 2026-11-18.

## Why
- Since 2026-11-16: 220 gate runs, 141 cancelled, 21 succeeded.
- Every promotion pushes the same commit to `staging` and `main` and runs the full gate twice.
- Task-branch runs fail by design until approval trailers are added, so they are noise.
- The Windows job rebuilds its dependencies on every main/staging push (over 1 h when uncached).
- The backup job on `main` was red for 13 h without anyone noticing.

## Acceptance criteria
1. **One full gate run per promotion.** Choose and document one rule, for example: the gate runs on `staging` (and on
   integration branches), and `main` is fast-forwarded to an already-verified SHA with no second full run, only a
   cheap SHA check or "already verified" marker. The backup job keeps running on `main`.
2. **Task branches** run the fast tier only. The full tier runs on integration branches, and on task branches only
   when the commit message or a label asks for it (e.g. `[full]`).
3. **Windows:**
   - a nightly scheduled run plus `workflow_dispatch`, binding on its own result;
   - removed from every staging/main push;
   - the vcpkg binary cache keyed so that branches share it.
4. **Monitoring:** a small status script or workflow summary that lists the latest result of **every** workflow on
   `main`, so failures cannot hide; documented in `docs/process/GATE.md`.
5. Show the effect: the run count and runner-minutes for one promotion, before vs after (estimate from recorded runs).
6. No check removed or loosened; the same checks still run once.
