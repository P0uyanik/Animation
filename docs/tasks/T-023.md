# T-023: automated quality gate, Phase 1 (owner-approved 2026-11-16)

Goal: every task branch and its trial merge with `main` are checked identically and automatically; the Supervisor
reads only a short summary. Frozen assets and quality thresholds are protected; backups are verified. **No automatic
merge into `main`, no weakening of any check, no history rewrite, no loss of work.**

## Components
1. `tools/check_all.py`, the single entry point for agents and CI.
   - Fast tier (always): C++ build, `ctest`, `plush_tests`, Python tests, `tools/check_doc_links.py`, plus items 2–4.
   - Blender tier (only if character, material or render paths changed, or `--blender <exe>` is given):
     `verify_charsys.py`, `test_export_engine.py`, the face, groom, garment and material-preset tests, and the boy
     fingerprint.
   - Output: a summary of at most 10 lines (PASS/FAIL per check, details only for failures), JSON, exit code 0/1.
   - Runs on Linux and on Windows.
2. `tools/frozen_manifest.txt`: git blob IDs (independent of line endings) for boy 1.0.0, 1.1.0 and v6, F09/H28,
   `tests/data`, the image baselines, and `docs/references` videos and sheets. Any change → hard FAIL.
3. `tools/guarded_paths.txt`: thresholds and targets (`VISUAL_TARGET.md`, preset `targets`, tolerances), test files,
   `check_all.py`, both lists, and `.github/workflows/`.
   - A change → FAIL "REQUIRES SUPERVISOR APPROVAL".
   - It passes only when a commit on the branch carries the trailer `Supervisor-Approved: <path>`, added by the
     Supervisor.
4. Shared-systems lint: character IDs and names (from `assets/characters/*`) must not appear in shared code
   (`engine/`, `apps/`, `pipeline/charsys/` except character data, `pipeline/clips/`). Existing occurrences go in a
   baseline allowlist; only new ones fail.
5. `.github/workflows/checks.yml`, triggered by a push to `t-*`, `integration/*` and `main`.
   - Trial merge: `git merge --no-commit origin/main` inside CI only (never pushed); checks run on the merged result.
   - Merge status in the summary: `clean` / `CONFLICT in <files>` / `clean, tests FAIL after merge`.
   - Summary as one comment on PR #2; small renders as artifacts.
   - Security: least privilege (contents read; issues and pull-requests write); no secrets; actions pinned by SHA;
     OIDN and bpy pinned with checksums; CI never writes to branches; concurrency cancels superseded runs;
     job timeouts.
6. GitHub ruleset (applied by the Supervisor after owner approval): no force-push and no deletion on `main`, `t-*`
   and `relay-channel`.
7. Verified backups.
   - A workflow after every push to `main` and daily: a `git bundle --all`, checked with `git bundle verify`, uploaded
     as an artifact (maximum retention).
   - The relay keeps a verified bundle in `D:\Animation\backups` (rotation 7).
   - A restore into an empty folder is tested once.

## Workflow rules (add to `docs/process/WORKFLOW.md`)
1. Work areas: before dispatch, the Supervisor compares the planned file lists. Parallel tasks never share files.
   Central files (`presets.json`, `build_character.py`, character specs) belong to one active task at a time.
2. Conflicts:
   - Textual and hidden conflicts: the agent that owns the branch merges `main` into its branch (no rebase, no
     force-push), runs `check_all` and pushes; it is triggered automatically by the CI report.
   - Content conflicts: the Supervisor decides in one line.
   - Product questions go to the owner.
3. Merges into `main`: only the Supervisor, on a CI-green integration commit, with owner approval (batches allowed).
4. Never lose work: no rebase, force-push or branch deletion; work in progress is always committed and pushed.

## Acceptance
1. `check_all` runs identically in the cloud and on Windows; current `main` is green.
2. Local simulations on temporary commits (nothing pushed) each go red:
   - a change to a frozen file;
   - a new character name in shared code;
   - a changed threshold, until approved;
   - a broken C++ test;
   - a textual merge conflict;
   - a hidden conflict (green alone, red after merge).
3. The workflow runs on a test branch: the PR #2 summary is at most 10 lines with the merge status, and renders are
   downloadable.
4. A backup is created, verified and restored.
5. No existing test or threshold is changed; no data is lost.
