# Quality gate, claims, regression and backups (T-041)

How the delivery plan's safety rules ([DELIVERY_PLAN.md](DELIVERY_PLAN.md) §3, §5, §8.1) are enforced. Everything
here runs in `tools/check_all.py` (locally) and in `.github/workflows/checks.yml` / `backup.yml` (GitHub).

## 1. The gate (`tools/check_all.py`)

```
python tools/check_all.py --base origin/staging [--blender <blender>] [--task T-NNN] [--full]
```

At most ten summary lines; details in `build/check-all/check_all.json` and `build/check-all/logs/`.

| Line | What it checks |
| --- | --- |
| Frozen assets | `tools/frozen_manifest.txt` blob IDs and frozen scopes |
| Guarded paths | changes to `tools/guarded_paths.txt` entries need a `Supervisor-Approved: <path>` trailer |
| Write-set | a task branch (`t-NNN-…`) changes only files inside its claim in [OWNERSHIP.md](OWNERSHIP.md) (diff vs the merge base with `origin/staging`); other branches: not applicable |
| Shared-systems lint | no new character names in shared code |
| C++ build | CMake + Ninja (OIDN 2.3.3 prebuilt via `PLUSH_OIDN_ROOT`) |
| C++ tests | CTest (incl. the frozen image regressions) and `plush_tests` |
| Python tests and links | Python unit tests (incl. `tools/regression/tests/test_gate_tools.py`, `tools/cleanup/run_tests.py` once present, and the cast check, §1.1) and Markdown links |
| Blender tier | fast tier: reported as "not required: fast tier"; full tier: verify_charsys, determinism, export, face, hair/groom, garment, material presets **and the all-character regression** (§3) |
| Merge status | CI trial merge |

### 1.1 Cast check: evaluations use the current character versions (T-062)

`python tools/check_cast.py [--base <ref>]`, run in the fast tier through
`pipeline/production/tests/test_run_shot_current.py` (reported on the "Python tests" line). The current version of a
character is the one `docs/evaluation/characters/fidelity_baseline.json` builds (spec + overrides), the same list the
all-character regression uses (§3). Shots name it with the cast reference
`{"character_id": "<id>", "version": "current"}`; `pipeline/production/run_shot.py` resolves it (the published master
when that version is published, otherwise a build from spec + overrides) and records the resolved version in
`run_shot.json`, `prepare.json` and `cast.json`.

- **Evaluation shots** `content/scenes/eval/**` (idle, walk, reach + touch + wave, wave, hand-over, emotions;
  generated by `content/scenes/eval/make_eval_shots.py`): every cast entry must be `"current"`. Every character in
  the fidelity baseline must appear in at least one of them (a newly buildable character is added there).
- **New evidence shots** `docs/evaluation/**/shot*.scene.json` added since the merge base with `--base` (default
  `origin/staging`): every cast entry is `"current"` or an explicit source of the current version.
- A pinned non-current version (`version_dir` or spec + overrides) FAILS unless that cast entry has a non-empty
  `"legacy_reason"` (e.g. an old-vs-new comparison or a frozen regression that needs the old version).
- **Exempt:** the engine unit-test packages in `tests/data` (frozen; packages, not shots) and shots that existed before
  T-062 (`episodes/**`, older `docs/evaluation/**` evidence): they record what was rendered at the time and are not
  rewritten.

The Blender tier is never skipped silently: on the fast tier it says so; on the full tier a missing Blender is a
FAIL; on Windows CI it states that it runs on the linux job; on a task branch without `[full]` it states that it
runs on the `integration/*` gate (§5).

## 2. Tiers (`tools/regression_paths.txt`, guarded)

`<fast|full> <glob>` rules, first match wins, **unknown paths are full**, one full path makes the change set full.
Full: `pipeline/**`, `assets/**`, `content/**`, `engine/**`, `apps/render-cli/**`, `tests/regression/**`,
`tests/data/**`, the regression machinery itself, fidelity tools, references. Fast: isolated C++ tests, studio UI,
build configuration, `tools/**`, `.github/**`, `docs/**`, root Markdown. A new shared module is added once, as
`full`, above any broader `fast` rule. `python tools/regression/tiers.py --base <ref>` prints the decision.
`--full` raises the tier; nothing lowers it.

## 3. Full regression and unchanged-character guard (`tools/regression/`)

```
python tools/regression/run.py --blender <blender> --out <dir> [--character <id>] [--base origin/main]
```

For **every** character folder in `assets/characters`, in parallel. A folder with a spec but no regression config
(an entry in `fidelity_baseline.json`) is a FAIL. A folder with references but no spec yet (reference intake, e.g.
`girl_white_hair_blue_dress`) is reported as "references only, not buildable yet". The steps per character: build (spec + the overrides of its current version, from `fidelity_baseline.json`), format-2 fingerprint
(0.01 mm), engine export, fixed-camera renders (`views.json`: four turnaround views + face close-up at the head
bone, 320 px, 16 samples, OIDN, seed 0, the shared render calibration), fidelity (drop > 2 points = FAIL).

Comparison ref (`--against origin/main`, CI and `check_all.py`): every character is also built from `origin/main`
(a temporary git worktree) **on the same machine** with the same measuring tools (fingerprint tool, cameras).
Builds are bit-reproducible on one machine but not across CPU families (T-041 finding: the boy's legacy
`hair_clumps` mesh differs between GitHub runners), so identity is checked against `main` built here, not against
files made elsewhere.

Approved baselines: `docs/evaluation/regression/baselines/<id>/<spec version>/` (`golden.json`,
`fingerprint.json`, `images/*.png`), guarded. With a comparison ref they are compared for information (and must not
be stale); without one (`run.py` without `--against`) the comparison against them is strict.

- **Unchanged character** (its spec/override files are not in the diff vs `--base`): must be identical to `main`
  built on this machine: fingerprint byte-equal, engine export equal (order-independent summary, see below), every
  render within the noise threshold. Any difference is a FAIL, even if it looks better. A missing or stale approved
  baseline (made from other spec inputs) is a FAIL too.
- **Changed character** (pin bump / look task, path B): differences from `main` and from the baseline are listed for
  the owner; only fidelity can fail. New baseline files come with the task (new files only) and need Supervisor
  approval.

Noise threshold (`tools/regression/render_noise_threshold.json`, guarded): measured with `run.py --noise` (every
character built and rendered twice from one commit): boy max rmse 1.7e-5, girl max rmse 0.0028 / 0.37 % changed
pixels (hair fibres). Threshold: rmse 0.006, changed pixels 0.8 % (about 2× the measured noise).

Engine export: two identical builds export the same geometry with a different triangle/vertex order and float noise
of about 1 ulp (≤ 1.1e-6), so neither `geometry.bin` bytes nor hashes of quantized positions are stable (a vertex
can land on either side of a rounding boundary; measured on the boy's `ear.L`). Against `main` built on the same
machine the two packages are compared directly: `character.json` exactly (without byte hashes), per mesh every
vertex matched within 0.01 mm, triangles equal as index sets, joints equal, weights and normals within 1e-4, other
buffers (morph targets) by count/mean/rms/min/max within 1e-5. Against a stored baseline (no package stored) only
that statistics summary is compared, for information.

## 5. CI (`.github/workflows/checks.yml`, `windows.yml`, `ci-status.yml`; run rules T-086)

Push to `t-*`, `integration/*`, `staging`, `main`. Jobs: **plan** (comparison base and trial-merge target: task
branches use `origin/staging`, `staging`/`integration/*` use `origin/main`; tier; "already verified" lookup),
**linux gate** (apt libraries, pinned OIDN prebuilt, pinned bpy, ccache; gate on the trial merge), **linux renderer**
(the one renderer-ON build, T-085), **regression \<character\>** (full tier only, one job per character, in
parallel; also uploads baseline candidates), **Gate verdict** (combines all reports into ≤ 10 lines, fails on any
FAIL, a missing report or a failed required job). Required check for the rulesets: **Gate verdict**.

Tiers per branch:

| Branch | Tier |
| --- | --- |
| `t-*` (task) | **fast**, whatever the paths. If the paths would need the full tier, the "Blender tier" line says so and that it runs on the `integration/*` gate (never silent). `[full]` in the head commit message runs the full tier on the task branch. |
| `integration/*` | decided by the paths (§2: one full path makes it full); `[full]` raises it. This is the one full gate run of a promotion. |
| `staging`, `main` | the same commit already passed → no second run (§5.1); otherwise the paths decide, as on `integration/*`. |

### 5.1 One full gate run per promotion

A promotion is: `integration/<x>` passes the gate, then `staging` and `main` are fast-forwarded to **that same
commit** (pushed together). The rule:

- On a **push** to `staging` or `main`, the plan job runs `tools/ci_status.py verified` for the pushed SHA. If a
  Quality gate run **for exactly this commit** succeeded on `integration/*` (for `main` also on `staging`) with
  every required job green (plan, linux gate, linux renderer, Gate verdict, and — when the promoted range
  `<previous tip>..SHA` contains a full path — every `regression <character>` job), all gate jobs are skipped and
  **Gate verdict** passes with `PASS Already verified: Quality gate run <id> on <branch> …` (a link to that run).
  The required check on the commit is therefore green from the run that actually tested it.
- `main` waits (up to 150 min, polling once a minute on one small runner) for a run of the same commit that is still
  in progress on `staging`/`integration/*`; `staging` waits only for `integration/*`, so they never wait for each
  other. If the newest finished run for the commit **failed**, the verdict fails with that run's link (no rerun).
- No run for this commit (e.g. a direct push) → the full gate runs on that branch exactly as before. A
  `workflow_dispatch` run always runs the full gate.
- The backup workflow (`backup.yml`, §6) is unchanged and still runs on every push to `main` and `staging`.

### 5.2 Windows (`.github/workflows/windows.yml`)

Not part of any push run. **Nightly** on `main` (03:43 UTC) and **`workflow_dispatch`** on any branch (same base and
trial-merge rules, `.github/scripts/select_base.sh`): `tools/check_all.py` C++ and Python tiers with vcpkg (the
Blender tier and the regression are reported as running on linux). **Binding on its own result**: a failing gate
fails the workflow, which then shows red in the CI status (§5.3) until a run passes. vcpkg binary cache key:
`vcpkg-x64-windows-<MSVC version>-<vcpkg ports commit>-<hash(vcpkg.json, vcpkg-configuration.json)>` (no branch or
commit), saved only from `main`, so every branch restores the same packages (GitHub caches from the default branch
are visible to all branches).

### 5.3 Monitoring: latest result of every workflow on `main`

```
python tools/ci_status.py status [--branch main]     # needs GH_TOKEN/GITHUB_TOKEN or the gh CLI
```

One line per workflow in the repository: `PASS|FAIL|WARN <workflow>: decisive <newest completed result that was
not cancelled/skipped>; newest <newest run>`. Workflows that never ran on `main` (e.g. `relay-notify`, which lives
on `relay-channel`) are listed with the branch they last ran on; a workflow whose last 30 runs were all cancelled is
a WARN. Exit 1 on any FAIL. The **CI status (main)** workflow (`ci-status.yml`) runs it after every completed `main`
run of the other workflows, daily at 06:41 UTC and on demand, writes the table to its job summary and is red while
any workflow is red on `main`.

### 5.4 CI speed (T-127): Blender shards, pinned apt cache, superseded runs, durations

- **Blender shards** (full tier). The Blender tier of `tools/check_all.py` is a list of named units
  (`BLENDER_UNITS`: the same commands, arguments and thresholds as before, in the same order). On the full tier the
  plan job reads `tools/ci/blender_shards.json` (4–6 shards) and the **blender shard K** jobs run
  `check_all.py --blender-shard K/N --full --regression-external …` in parallel; the linux gate then reports
  `Blender tier: … runs in N blender shard jobs` and lists the units in its report. **Gate verdict** fails unless the
  `blender` job succeeded (a cancelled, skipped or failed shard is FAIL), every report `quality-blender-1..N` is
  present and names its shard, and the shards' units are exactly the linux report's unit list, each once. Every unit
  builds its own characters; nothing built is reused between units or shards (owner decision T-127, item 6 not
  approved). A unit that reads another unit's output in the same run (`face` reads the `charsys` master, as before)
  must sit in the same shard; the plan is rejected otherwise, and an unassigned unit runs in shard 1. The shard with
  `shot-eyes`/`emotions` also builds the `plush-render` target (the bake engine).
  Proof that the commands are identical: `python tools/ci/blender_inventory.py` (also run by the Python tests via
  `tools/ci/tests/test_t127_shards.py`); evidence in `docs/evaluation/ci/T-127/`.
- **Fallback (pre-T-127 path)**: repository variable `PLUSH_CI_BLENDER_SHARDS=off`, or `[unsharded]` in the head
  commit message: no shard jobs, the linux gate runs the whole Blender tier in-process exactly as before. Locally,
  `tools/check_all.py` without `--blender-shard` always runs every unit in order.
- **Pinned apt cache**: `install_ci_dependencies.ps1 -AptCache <dir>` (linux gate, renderer, the shard that builds
  `plush-render`, backup fast tier). Cache key `apt-<job>-<ImageOS>-<ImageVersion>-<hash(ci-dependencies.json)>`.
  On a hit the recorded `.deb` files are checked against `manifest.json` (sha256 each) and installed with `dpkg -i`,
  without contacting the Ubuntu mirrors; the log prints `digest sha256:<manifest hash>`. On a miss, a runner image
  update or any cache problem the mirror install runs as before and refills the cache: `apt-get update`/`install` with
  bounded retries and backoff (`Acquire::Retries=3`, then 15/45 s), and if the runner's mirror stays down the same
  archive from `archive.ubuntu.com`, then `mirrors.edge.kernel.org` (security.ubuntu.com untouched). The bpy
  wheel and OIDN stay in the checksum-verified pinned-download cache.
- **Superseded runs**: a newer push cancels the running Quality gate only on `t-*` and `integration/*`. `main`,
  `staging`, `workflow_dispatch` runs, the backup workflow, nightly Windows and every scheduled workflow are never
  cancelled (each `main`/`staging`/manual run has its own concurrency group).
- **Per-test durations**: every command `check_all.py` runs is timed (`durations` in each `check_all.json`, and
  `durations.txt` next to it, slowest first); the Gate verdict job summary shows the slowest 25 across all jobs.
  Parallel shard jobs finish sooner but use more runner minutes per run (each installs bpy); see the T-127 numbers.

### 5.5 Batch promotions (T-127): one gate run for several finished tasks

1. Collect the finished task branches that are READY (each passed its own fast-tier gate, write-sets disjoint or
   reviewed together).
2. Create one `integration/<batch-name>` from `origin/main` (or the previous staging tip) and merge each task branch
   into it in the order of the ledger, resolving nothing silently (a conflict stops the batch for that task).
3. Push `integration/<batch-name>` once all tasks are merged: this is the one full gate run of the batch (§5.1).
   Pushing intermediate states is allowed; the newer push cancels the older integration run (§5.4).
4. Green **Gate verdict** on the integration tip → fast-forward `staging` and `main` to **that same commit** together
   (§5.1: "Already verified", no second full run). Red → remove the failing task from the batch (new integration
   branch without it, or a revert on the integration branch) and run the gate again; never promote a partially green
   batch, and never mark a task done whose change was not in the verified commit.
5. Record the batch in the ledger: tasks, integration branch, verified commit and gate run link.

## 6. Backups (`.github/workflows/backup.yml`, plan §8.1 layers 1–2)

- **Tags:** every push to `main`/`staging` and every pushed backup request `archive/backup-<UTC>-<branch>` creates
  `backup/<UTC yyyymmddTHHMMSSZ>/<branch>` (`.github/scripts/backup_tags.py`; Actions token with `contents: write`, because
  cloud sessions cannot push tags). A tip already tagged for that branch is not tagged again. Tags are never deleted.
- **Bundle:** on every push to `main`, nightly (02:17 UTC) and on demand: bare snapshot of all remote branches and
  tags → `git bundle create --all` → `git bundle verify` → `.sha256` → restore test (mirror-clone the bundle,
  `git fsck --full`, every branch/tag SHA equal to the snapshot, then the fast tier on the restored `main`) →
  artifact for 90 days (`tools/backup_repository.py`). A failed restore test fails the workflow.
- **Release:** Sunday's nightly run (or on demand) publishes `backup-<YYYY-MM-DD>` with the bundle; the 8 newest and
  the first of every month are kept, older weekly releases lose the release entry, never the tag.
- Restore: `git clone --mirror <bundle> restored.git`, or from a tag: `git push origin backup/<…>/<branch>:refs/heads/<branch>`.
